# 4.13.3 Currency picker

- **Status:** `done`
- **Goal:** the user picks a bank’s currency when creating it, and can change that currency later. The stored number does not change.
- **Depends on:** [`4.13.2`](4.13.2-currency-display.md).
- **Read with this file:** [`requirements.md`](../requirements.md) (Currencies and FX), [`areas/telegram.md`](../areas/telegram.md), [`areas/service.md`](../areas/service.md), [`areas/persistence.md`](../areas/persistence.md).

## In scope

### `/newbank`

Today: name → duplicate check → “Count in total?” → insert. After this step: name → duplicate check → include yes/no → **currency** → insert.

- Do not insert the bank before the currency is valid. Hold the name and the include flag in the FSM. `/cancel` on the currency step writes nothing and does not change `last_currency`.
- `/newbank Travelling` is still the whole name. Do not parse a currency or a yes/no off that line.
- The currency step edits the same wizard prompt (hygiene). Typed codes are sweep-deleted. No emoji on the prompt.

Prompt (same meaning in `en`, `ru`, `uk`, `md`; this is the English source):

```text
Choose a currency.
For a different one, send its code, for example UAH.
```

Buttons, one row, left to right: `€`, `$`, `USDT`. Callbacks carry `EUR`, `USD`, `USDT` (`v1:ccy:EUR` and the same for the other two).

If `users.last_currency` is a valid code and is not `EUR`, `USD`, or `USDT`, add a fourth button on that row, label = the code (`UAH`). A missing or invalid stored value shows three buttons. Never duplicate a default button. Order stays `€`, `$`, `USDT`, then the extra code.

Typed text goes through `domain.ParseCurrency`. Invalid input edits the prompt and stays on the step:

```text
That is not a currency I can use. Choose a button, or send a 3-letter ISO code such as UAH. USDT is also allowed.
```

- On success, one transaction inserts the bank with that code and sets `users.last_currency` to it.
- `CreateBank` takes the validated code. It no longer reads `DEFAULT_CURRENCY`. Keep parsing the env var so existing process configs still start; it does not choose a bank’s currency. README: say the variable is accepted and ignored.
- Created-bank outcome names the currency with the display label (`$` or `UAH`), still without a fake non-zero balance.

### `/currency`

- New command, domain const next to `rename` / `transfer`. `setMyCommands` description in English: `change a bank's currency`. Listed in `/help` in all four catalogs. Slash name stays `currency`.
- Empty `/currency` is an empty-wizard command for the pending-queue compact rules, same class as `/rename`.
- Flow: pick bank → the same picker → confirm when the code differs. Shortcut `/currency Travelling` opens the picker for that bank.
- Args use the `/rename` rule: try the full remainder as the bank name; if that bank does not exist, the first word is the bank and the rest is a currency code. `/currency Travelling UAH` with a valid code skips the picker and goes to confirm. A bad code on that shortcut is the invalid-currency outcome, not a bank named `Travelling UAH`, when `Travelling` exists and the remainder is one token.
- Picking the bank’s current code does **not** open confirm, does **not** write an operation, and does **not** touch the balance. Outcome: `"Travelling" already uses $.` Still set `last_currency` to that code.
- When the code differs, confirm before any write. English source:

```text
"Travelling" is $100.00. It will show as 100.00 UAH. The number does not change. Confirm?
```

  Buttons are the existing localized Yes / No. Yes writes. No outcome: `Okay, the currency stays $.` (current label). `/cancel` is still `Canceled.` Neither No nor `/cancel` writes.

- Yes, in one `Transactor` transaction: set `banks.currency`, set `users.last_currency`, append one operation. Balance cents stay identical. There is no exchange rate on this path.
  - Operation type `currency` (new domain const).
  - `amount_cents` = current balance, `balance_after_cents` = same balance.
  - `meta` = `USD -> UAH` (codes, same `Old -> New` shape as rename).
- Success outcome, one leading ✅: `"Travelling" now uses UAH. Balance is 100.00 UAH.`
- Migration `003_operation_currency.sql`: extend the operations `type` check to include `currency`. The table constraint from `001_init.sql` is named `operations_check`. Do not drop other checks.

### Repository

- `UserRepository.SetLastCurrency`. `Upsert` still must not overwrite `last_currency`.
- Service method for the change, scoped by `userID`, unknown bank → the usual not-found error.

## Out of scope

- Converting the balance when the currency changes (the user moves money with `/transfer`)
- Cross-currency `/transfer` ([`4.14.2`](4.14.2-fx-transfer.md))
- A history screen (`4.10`)
- Parsing a currency out of `/add`, `/spend`, `/set`, or `/transfer`

## DoD

- New bank stores the chosen code and updates `last_currency`
- Fourth button appears only for a non-default last code, and disappears once the last code is `EUR`, `USD`, or `USDT` again
- Invalid text does not create or recode a bank
- Currency change keeps `balance_cents` and writes one `currency` operation
- Same-code choice writes no operation
- `make test-unit`, `make lint`, and `make test-integration` pass

## Tests

- Service: change `USD` → `UAH` keeps cents, writes `meta` `USD -> UAH`, sets last currency; same code writes nothing and still sets last currency; other user’s bank is not visible.
- Parse/picker cases can stay in domain tests from `4.13.1`; add handler tests for button order (3 vs 4), invalid text staying on the step, and `/newbank` not inserting before a valid code.
- Integration: `currency` is accepted by the operations check; a change row is readable.
