# 4.3.1 Hosting packaging

- **Status:** `todo`
- **Goal:** the repo can deploy to Railway **only after CI `common` is green**. No live production yet.

## In scope

- GitHub Actions **deploy** job in [`.github/workflows/ci.yml`](../../../.github/workflows/ci.yml) (same workflow so `needs: common` is real):
  - runs on push to `master` / `main` only (not pull requests, not `workflow_dispatch` unless that is a no-op)
  - `needs: common`
  - deploys the existing `Dockerfile` with Railway CLI or official action
  - fails the workflow if deploy fails
  - secrets: `RAILWAY_TOKEN` and any project/service id the CLI needs — documented in README, empty in this step until `4.3.2`
- Until secrets exist, the deploy job must **skip cleanly** (not fail) so `master` CI stays green. Document that `4.3.2` fills the secrets.
- `railway.toml` (or `railway.json`) at repo root: Docker builder, start command is image `ENTRYPOINT`, **no** public networking, restart on failure. Comment in the file: replica count is 1; horizontal scale is `4.9`.
- README production section: host is Railway; worker not a web service; sleep off; env vars (`BOT_TOKEN`, `DATABASE_URL`, `REDIS_URL`, optional `ADMIN_TELEGRAM_ID` / `LOG_LEVEL` / `TRIAL_DURATION` / `DEFAULT_CURRENCY`); private URLs for the app; how logs are tailed; how deploy is triggered; **two long-poll processes fight**.
- `.env.example`: comment that hosted Postgres should use TLS (`sslmode=require` or the vendor URL as issued). Do not put production URLs in git.
- Document that Railway’s GitHub auto-deploy (if enabled) must be **off** so Actions is the only deployer.

## Out of scope

- Creating the Railway project, databases, or GitHub secrets (`4.3.2`)
- Webhook server, HTTP health, metrics SDK, second `cmd/`
- Changing Postgres/Redis adapters, pools, or FSM TTL
- Compose as production

## DoD

- A push to `master` without Railway secrets: CI `common` green, deploy job skipped
- A reviewer can see in git how production will be deployed and that replica count is 1
