# 4.9 Load resistance

- **Status:** `todo`
- **Goal:** survive public traffic beyond one bot process: per-user token bucket / rate limit, Cache, **app replicas**, and Postgres **scale-up** (partitioning if `operations` needs it; PgBouncer if connection storms).

## Already done in `4.1` — do not rebuild

- Connection pool and session timeouts
- `SELECT … FOR UPDATE` on in-tx bank reads; transfer lock order; deadlock retry
- Access indexes including `operations (user_id, created_at DESC)`

## In scope (when this step starts)

- Token bucket / rate limit per Telegram user
- More than one bot replica (in-memory FIFO in `3.7` is not enough across processes; Redis from `4.2` or equivalent)
- Range-partition `operations` (likely on `created_at`) **if** volume warrants it; schema in `4.1` used `BIGINT IDENTITY` + `TIMESTAMPTZ` so this is an `ALTER`, not a rewrite
- PgBouncer or pool retune if the host connection limit is the bottleneck
- Do not pre-build this in Stage 3 or in `4.1`

## Out of scope

- Replacing Postgres
- Inventing microservices unless this step or `4.17` shows a need (`4.21` is still a modular monolith first)
